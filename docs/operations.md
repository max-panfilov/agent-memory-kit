# Эксплуатация

## Запуск и миграции

`docker compose up --build -d` последовательно запускает:

1. PostgreSQL 17 с healthcheck;
2. `migrate` с `migrations/0001_initial.sql`;
3. `seed` с идемпотентным добавлением синтетических проектов и приложений;
4. MCP с проверкой `/health`.

Миграция не удаляет существующие события. Seed использует `ON CONFLICT DO NOTHING` и не перезаписывает ручные изменения проектов.

Основные переменные:

| Переменная | Назначение |
|---|---|
| `AGENT_MEMORY_ROOT` | Корень ресурсов; обязателен, если запуск не из корня репозитория |
| `AGENT_MEMORY_DATABASE_URL` | Строка подключения к PostgreSQL |
| `AGENT_MEMORY_CONTENT_ROOT` | Корень синтетического каталога |
| `AGENT_MEMORY_PRINCIPALS_PATH` | JSON с хэшами и областями |
| `AGENT_MEMORY_STDIO_CLIENT_ID` | Локальный принципал для STDIO |
| `MCP_PORT` | Loopback-порт HTTP, по умолчанию 8775 |

Не выводите `AGENT_MEMORY_DATABASE_URL` в логах: она содержит пароль.

## Проверка состояния

```sh
curl --fail http://127.0.0.1:8775/health
```

Health показывает версию, снимок документов и отсутствие semantic provider. Он не заменяет MCP smoke и не подтверждает возможность восстановления.

Полная проверка в отдельном Compose-проекте:

```sh
ci/verify.sh
```

Скрипт выбирает уникальное имя проверочного проекта независимо от `COMPOSE_PROJECT_NAME` оболочки и удаляет только созданные им синтетические ресурсы, включая тома. Работающее демо и параллельные проверки используют другие namespaces.

## Резервная копия

```sh
PYTHONPATH=src python3 -m agent_memory_kit.backup
```

Скрипт создаёт каталог `backups/<UTC timestamp>/` с:

- `agent-memory.dump` — custom-format PostgreSQL;
- `manifest.json` — размер и SHA-256;
- `receipt.json` — результат изолированного восстановления;
- `tampered.json` — отрицательный контроль манифеста.

Каталог игнорируется Git и доступен только владельцу. Восстановление выполняется в новом одноразовом экземпляре PostgreSQL, который затем удаляется. Сравниваются количество событий и пары `id`/`payload_hash`. Отдельно подтверждается, что исходная база не изменилась.

Проверить существующий манифест:

```sh
PYTHONPATH=src python3 -m agent_memory_kit.backup --verify-only backups/<timestamp>/manifest.json
```

Скрипт не создаёт расписание и внешнюю копию. Для реальной эксплуатации добавьте зашифрованное внешнее хранилище, политику хранения копий и регулярные проверки восстановления.

## Неизвестный исход записи

При неизвестном исходе из-за ошибки соединения сервер возвращает `MEMORY_WRITE_OUTCOME_UNKNOWN` и не предполагает, что записи нет. Выполните `read_project_memory` с исходным UUID. Повторяйте запрос только с той же полезной нагрузкой. Не удаляйте старые события или аудит для «упрощения» повтора.

Если PostgreSQL отклонил сериализацию и readback не нашёл записи, возвращается `MEMORY_WRITE_RETRY_REQUIRED`: эта транзакция отменена. Повтор допустим только с исходным UUID и той же полезной нагрузкой; автоматического повтора нет. Конфликт UUID означает существующую запись с другим payload, а не временный serialization abort.

## Обновление

1. Сохраните резервную копию и проверьте восстановление.
2. Зафиксируйте текущий Git SHA и digest образов.
3. Обновите зависимости отдельным изменением и зафиксируйте `uv.lock`.
4. Выполните `ci/verify.sh` на новом SHA.
5. Обновите только проверенный образ и проверьте health и MCP smoke ещё раз.

Откат приложения не восстанавливает автоматически прежнюю схему БД и не удаляет новые события. Миграции и совместимость отката оцениваются отдельно.

## Удаление демо

```sh
docker compose down -v
```

Эта команда удаляет volume текущего Compose-проекта. Выполняйте её только для синтетического демо и никогда как общую очистку Docker-хоста.
